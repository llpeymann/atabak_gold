# طلای اتابک — ربات گزارش بازار (Atabak Gold market bot)

سرویس زمان‌بندی‌شده‌ای بر پایه **NestJS 11** که قیمت‌های بازار طلا، سکه و ارز را از یک API بیرونی می‌گیرد و
به‌صورت پیام متنی منظم در کانال **بله** (و در صورت تنظیم، **تلگرام**) منتشر می‌کند.

A scheduled NestJS service that publishes gold, coin and currency market prices to a **Bale**
channel (and optionally a mirrored **Telegram** channel).

---

## 1. Overview / نمای کلی

* منبع قیمت: یک API بیرونی JSON که با `PRICE_API_URL` معرفی می‌شود.
* کانال‌های انتشار: **بله** (اجباری) و **تلگرام** (اختیاری).
* زمان‌بندی: ساعت ۰۸:۰۰ تا ۲۱:۳۰ هر نیم‌ساعت + پیام پایانی ۲۲:۰۰ + گزارش پوستر سه‌بار در روز — همه به وقت تهران.
* بدون دیتابیس، Redis یا صف: وضعیت فقط شامل آخرین قیمت‌های منتشرشده در حافظه است (برای محاسبه روند روزانه).
* فقط یک endpoint عمومی برای پایش سلامت: `GET /health`.

## 2. Architecture

```
┌──────────────────────┐
│  Price API (external)│──► PriceService ── transport only: timeout + bounded retry + raw payload
└──────────────────────┘         │  (raw JSON, never leaves this layer)
                                 ▼
                        ┌────────────────────────────────────────────┐
                        │  MarketEngineService (single entry point)   │
                        │  Parser → Normalizer → Schema/Symbol/Number │
                        │  → Sanity/Anomaly → Market State → Change   │
                        │  → Daily stats → Publish / Reject(+reason)  │
                        └─────────┬───────────────────────────────────┘
                                  ▼  PublishableMarketUpdate (only approved domain objects)
                        ┌─────────────────────┐
                        │  BotService (cron)  │  Asia/Tehran schedules, single publication gate
                        └─────────┬───────────┘
             ┌────────────────────┼────────────────────┐
             ▼                    ▼                    ▼
   PriceMessageBuilder     PosterService      MarketStateStore
   (channel message)      (poster text)     (JSON persistence, restart-safe)
             └────────────────────┼────────────────────┘
                                  ▼
                           BaleService ──► Bale API  (required)
                                     ├──► Telegram API (optional)
                                     └──► admin anomaly alerts (explicit chat id)
```

| `src/alerts/` | هشدار قیمت (فاز ۳): مدل و store اتمیک، ارزیاب خالص، سرویس دامنه، قالب‌بندی فارسی، سرویس ارسال، موتور ارزیابی متصل به وضعیت بازار |
| `src/intelligence/` | هوش بازار (فاز ۴): ساخت snapshot فقط‌خواندنی از وضعیت تأییدشده فاز ۱ (گزارش روزانه، حرکت، زمان آخرین بروزرسانی، خلاصه شمارشی) |
| `src/bot/ux/market-format.ts` | قالب‌بندی فارسی صفحه‌های هوش بازار (فقط نمایش؛ هیچ محاسبه/اعتبارسنجی/تغییر داده) |
| `src/common/` | ابزارهای مشترک: واحد پول (ریال/تومان)، برندینگ، زمان تهران، ایمنی لاگ، HTML |

**مسیر داده در فاز ۲:** آپدیت کاربر → `UpdatePollerService` (long-poll) → آداپتر پلتفرم →
`BotUxService` (روتر + callback grammar) → `MarketViewService` (فقط خواندن از وضعیت فاز ۱) →
`ux-format` (متن فارسی) → آداپتر پلتفرم (ویرایش پیام؛ در صورت پشتیبانی‌نشدن، ارسال پیام تازه).
هیچ مسیری از لایه UX به API قیمت وجود ندارد و همین موضوع در تست‌ها اثبات شده است.

**مسیر داده در فاز ۳:** انتشار قیمت پذیرفته‌شده در فاز ۱ → `MarketEngineService` (لیسنر
`registerUpdateListener`، فقط قیمت‌های تأییدشده و پس از ذخیره‌سازی) → `AlertEngineService` (فقط
هشدارهای `ACTIVE` همان نماد) → `evaluateAlert` (تابع خالص) → `AlertService.reserveTrigger` (یک
بخش بحرانی: هشدار `TRIGGERED` + رکورد ارسال) → `AlertNotificationService` (ارسال با تلاش کراندار از
طریق انتزاع پلتفرم). هیچ مسیری از موتور هشدار به API قیمت وجود ندارد.

**مسیر داده در فاز ۴:** وضعیت بازار تأییدشده فاز ۱ → `MarketIntelligenceService` (یک‌بار خواندن هر نماد،
تبدیل قطعی به snapshot توصیفی) → `MarketViewService.buildIntelligence` → `market-format` (متن فارسی) →
آداپتر پلتفرم. این مسیر فقط‌خواندنی است: نه فراخوانی API، نه تغییر وضعیت، نه اجرای هشدار. فاز ۴ هیچ
وضعیت بازار دوم، cache، حلقه پس‌زمینه یا زیرساخت تازه‌ای اضافه نمی‌کند.

**واحد پول داخلی:** همه قیمت‌ها در واحد **ریال** نگه‌داری و با نام `priceInRial` منتقل می‌شوند. تبدیل واحد
فقط از طریق `src/common/money.ts` انجام می‌شود و هر عدد نمایش‌داده‌شده واحد خود را همراه دارد
(هیچ ابهامی بین ریال و تومان باقی نمی‌ماند).

## 4.1 خط لوله اعتبارسنجی قیمت (Phase 1)

هیچ قیمتی مستقیماً از API به کانال نمی‌رسد. هر چرخه از این مراحل قطعی می‌گذرد و هر رد شدن، دلیل صریح دارد:

| مرحله | مسئول | رد می‌کند وقتی |
| --- | --- | --- |
| Parse | `raw-payload.parser.ts` | بدنه JSON ساختار انتظاری را ندارد (`INVALID_SCHEMA`) |
| Symbol | `symbols.ts` (رجیستری واحد، ۱۶ نماد) | نماد در payload نیست (`MISSING_SYMBOL`) یا ناشناخته است (`UNKNOWN_SYMBOL`) |
| Normalize | `price-normalizer.service.ts` | مقدار null/NaN/Infinity/غیرعددی/منفی/صفر باشد (`INVALID_NUMBER`, `INVALID_PRICE`)؛ رشته‌های عددی و واحدها به قرارداد داخلی تبدیل می‌شوند |
| Sanity | `sanity-checker.service.ts` | خارج از بازه منطقی نماد (`OUT_OF_RANGE`) یا تغییر بیش از آستانه (`EXCESSIVE_CHANGE`) |
| State | `market-state.service.ts` | قیمت ردشده هرگز `currentPrice`/`lastValidPrice`/ساعات روزانه را تغییر نمی‌دهد |
| Publish | `market-engine.service.ts` | هیچ نماد اجباری تازه‌ای نباشد (`NO_FRESH_REQUIRED_SYMBOL` / `NO_ACCEPTED_PRICES`) |

* نمادهای اجباری (لنگر انتشار): `IR_GOLD_18K`، `IR_COIN_EMAMI`، `USD`. پاسخ ناقص فقط همان نماد را رد
  می‌کند، نه کل چرخه را؛ وضعیت معتبر قبلی آن نماد دست‌نخورده می‌ماند.
* آستانه‌ها برای هر نماد مستند و قابل بازنویسی‌اند (بازه منطقی، سقف درصد تغییر، سقف تغییر مطلق).
  نمادهای نقدی/ارز سقف تغییر کمتری دارند؛ دارایی‌های پرنوسان سقف بیشتری.
* روز معاملاتی بر مبنای `Asia/Tehran` تعریف می‌شود؛ اولین قیمت پذیرفته‌شده‌ی هر روز «open» آن روز است و
  هرگز با قیمت دیروز مقایسه نمی‌شود. مبنای مقایسه فقط `previousPrice` همان روز است؛ اگر وجود نداشته
  باشد جهت `UNKNOWN` و درصد تغییر `null` است (بدون رُندکردن زودرس، با دقت کامل).
* ناهنجاری‌ها به چت ادمین (`ANOMALY_ALERT_CHAT_ID`) اطلاع داده می‌شوند — نه به کانال کاربران — با
  `ANOMALY_ALERT_COOLDOWN_MINUTES` برای جلوگیری از اسپم (بدون Redis/صف).

## 4.2 لایه تجربه کاربری ربات (Phase 2)

ربات علاوه بر انتشار زمان‌بندی‌شده در کانال، یک بات تعاملی است. مسیر کاربر:

`/start` → منوی اصلی → 💰 قیمت لحظه‌ای | 🟡 طلا | 🪙 سکه | 📊 بازار | 🔔 هشدار |
⭐ علاقه‌مندی‌ها | 📢 کانال اتابک

* **تک‌منبع حقیقت قیمت:** همه صفحه‌ها فقط از «وضعیت بازار» فاز ۱ خوانده می‌شوند. لایه UX هیچ‌وقت
  مستقیم به API قیمت وصل نمی‌شود و هیچ قیمتی را بازمحاسبه یا جعل نمی‌کند؛ دکمه «↻ بروزرسانی» فقط
  وضعیت موجود را دوباره می‌خواند. نماد بدون داده به‌صورت «بدون اطلاعات معتبر» فهرست می‌شود.
* **قیمت کهنه:** اگر آخرین قیمت معتبر قدیمی‌تر از `PRICE_STALE_AFTER_MINUTES` باشد، هشدار
  «⚠️ آخرین قیمت معتبر …» نمایش داده می‌شود و هیچ‌وقت به‌شکل داده تازه نشان داده نمی‌شود.
* **علاقه‌مندی‌ها:** افزودن/حذف فقط از روی نمادهای ثبت‌شده (بدون تایپ دستی نماد)، بدون تکرار،
  سقف `MAX_FAVORITES`، و ذخیره‌شده در `USER_DATA_FILE` پس از ری‌استارت.
* **هشدار (Alerts):** بخش هشدار در فاز ۳ پیاده‌سازی شده است — صفحه ورودی، ویزارد ساخت، فهرست و
  مدیریت هشدارها (بخش ۴.۳).
* **دکمه‌های قدیمی:** هر callback ناشناخته یا منقضی به پیام «این گزینه دیگر معتبر نیست.» + دکمه
  «🏠 منوی اصلی» پاسخ می‌دهد و هرگز باعث خطا نمی‌شود. خطاهای فنی فقط در لاگ سرور ثبت می‌شوند.
* **لاگ رویداد:** رویدادهای پایه (`start`, `menu_open`, `prices_view`, `gold_view`, `coin_view`,
  `market_view`, `favorites_view`, `favorite_added`, `favorite_removed`, `channel_clicked`,
  `alerts_clicked`) و رویدادهای هشدار فاز ۳ (`alert_create_started`, `alert_created`,
  `alert_wizard_input`, `alert_invalid_target`, `alert_limit_reached`, `alert_duplicate`,
  `alert_updated`, `alert_enabled`, `alert_disabled`, `alert_deleted`, `alert_detail_view`,
  `alerts_view`, `alert_create_cancelled`) با شناسه کاربر و بدون هیچ داده شخصی در لاگ ثبت می‌شوند.

## 4.3 هشدار قیمت (Phase 3)

مسیر کاربر: `🔔 هشدار` → ➕ ساخت هشدار | 🔔 هشدارهای من → انتخاب نماد → نوع هشدار → وارد کردن عدد →
صفحه تأیید → ساخت. هر هشدار **یک‌بار** اجرا می‌شود و سپس وضعیت آن `TRIGGERED` می‌شود.

* **چهار نوع هشدار:** بالاتر یا برابر (`PRICE_ABOVE`)، پایین‌تر یا برابر (`PRICE_BELOW`)، افزایش
  درصدی (`PERCENT_INCREASE`) و کاهش درصدی (`PERCENT_DECREASE`). جهت درصدی صریح انتخاب می‌شود؛ عدد
  وارد‌شده در ویزارد همیشه قدرمطلق است.
* **خط لوله:** API بیرونی → موتور فاز ۱ → وضعیت بازار تأییدشده → ارزیابی هشدار → شرط → تصمیم اجرا →
  رکورد یکتا (Idempotency) → ارسال نوتیفیکیشن. موتور هشدار **هرگز** به API قیمت وصل نمی‌شود؛ تنها
  منبع قیمت، وضعیت بازار فاز ۱ است و داده‌های رد‌شده/ناهنجار هرگز ارزیابی نمی‌شوند.
* **شرط عبور (crossing):** برای هشدارهای مطلق باید قیمت *از* مقدار هدف عبور کند
  (`previous < target && current >= target` برای بالاتر و `previous > target && current <= target`
  برای پایین‌تر). پس هشدار تازه‌ساخته یا دوباره‌فعال‌شده فقط به‌دلیل «همین حالا درست بودن شرط»
  اجرا نمی‌شود؛ جهش (gap) و تساوی هم پوشش داده می‌شوند. اگر شرط همان لحظه ساخت برقرار باشد، در صفحه
  تأیید هشدار داده می‌شود و پس از تأیید، هشدار منتظر یک عبور تازه می‌ماند.
* **هشدار درصدی:** مبنا، آخرین قیمت معتبر (تازه و مثبت) در لحظه ساخت است و پس از آن هرگز خودکار
  بازمحاسبه نمی‌شود؛ فقط ویرایش هدف یا فعال‌سازی مجدد، مبنا را به‌صورت صریح به‌روز می‌کند. اگر قیمت
  معتبری موجود نباشد، ساخت هشدار درصدی با پیام روشن رد می‌شود.
* **چرخه عمر:** `ACTIVE` (ارزیابی می‌شود) → `DISABLED` (ارزیابی نمی‌شود، اما سهمیه را اشغال می‌کند) →
  `TRIGGERED` (پایان یک‌باره) و `DELETED` (حذف نرم؛ از فهرست، ارزیابی و سهمیه خارج می‌شود). ویرایش
  اتمیک است، ویرایش درصدی مبنا را تازه می‌کند و حذف نیازمند تأیید است.
* **مالکیت:** هر هشدار دقیقاً یک صاحب دارد و مالکیت در لایه سرویس/دامنه اعمال می‌شود (نه در UI).
  هشدار کاربر دیگر دقیقاً مثل «هشدار ناموجود» پاسخ می‌گیرد.
* **سقف‌ها:** `MAX_ALERTS_PER_USER` (پیش‌فرض ۵) روی `ACTIVE + DISABLED` اعمال و داخل همان بخش بحرانی
  بررسی می‌شود؛ ساخت هم‌زمان نمی‌تواند سقف را دور بزند. چون هشدار غیرفعال هم سهمیه را اشغال می‌کند،
  پیام سقف به کاربر می‌گوید برای ساخت هشدار تازه باید یکی را **حذف** کند (غیرفعال‌کردن سهمیه را آزاد
  نمی‌کند) — هم‌راستا با سیاست شمارش. هشدار تکراری (همان نماد + نوع + هدف) رد
  می‌شود، اما هشدارهای متفاوت مسدود نمی‌شوند.
* **اعتبارسنجی ورودی:** فقط نمادهای رجیستری فاز ۱ پذیرفته می‌شوند؛ اعداد با ارقام فارسی/لاتین و
  جداکننده‌های استاندارد خوانده می‌شوند و هر ورودی مبهم یا نامعتبر (خالی، منفی، صفر، `NaN`،
  بی‌نهایت، خارج از بازه مجاز نماد، درصد خارج از `ALERT_MIN_TARGET_PERCENT..ALERT_MAX_TARGET_PERCENT`)
  با پیام فارسی و بدون افشای جزئیات فنی رد می‌شود. مدل داخلی همیشه واحد استاندارد فاز ۱ (ریال/دلار)
  را نگه می‌دارد و تبدیل واحد فقط در نمایش انجام می‌شود.
* **نوتیفیکیشن:** اطلاع‌رسانی فقط از طریق انتزاع موجود پلتفرم (بله/تلگرام) انجام می‌شود و برای هر
  اجرا **دقیقاً یک** پیام ارسال می‌شود. رکورد ارسال (`PENDING`/`SENT`/`FAILED` با `attemptCount`,
  `sentAt`, `lastAttemptAt`, `lastError`) از وضعیت خود هشدار جدا است و همان یکی‌بودن را در برابر
  تکرار چرخه بازار، ری‌استارت و تلاش‌های مجدد تضمین می‌کند. تعداد تلاش‌ها کراندار است
  (`1 + ALERT_NOTIFICATION_MAX_RETRIES`) و هیچ صف بی‌پایانی وجود ندارد. اگر هشدار پیش از ارسال حذف
  شود، هیچ پیامی ارسال نمی‌شود. پس از ری‌استارت، ارسال‌هایی که وضعیت آن‌ها نامشخص است دوباره فرستاده
  **نمی‌شوند** (ارسال تکراری بدتر از گزارش وضعیت نامشخص است).
* **داده‌ها:** هشدارها و رکوردهای ارسال در `ALERTS_DATA_FILE` (یک سند JSON با نوشتن اتمیک) ذخیره
  می‌شوند؛ هیچ جدول/سرویس جدید یا زیرساخت اضافه‌ای (Redis/Kafka/…) اضافه نشده است. مهاجرت داده‌های
  قدیمی امن است و فایل ناشناخته/خراب باعث حذف داده نمی‌شود.
* **محدودیت‌های مستند:** بازه پذیرش قیمت هر نماد از رجیستری فاز ۱ گرفته می‌شود؛ بنابراین هدفی خارج از
  آن بازه پذیرفته نمی‌شود (چنین قیمتی هرگز توسط فاز ۱ تأیید نمی‌شود). مقایسه‌ها با دقت کامل انجام
  می‌شوند و رُندکردن فقط در نمایش است. تشخیص «عبور» بر مبنای مشاهدهٔ قبلی فاز ۱ است؛ اگر فاز ۱ برای
  یک قیمت پذیرفته‌شده مشاهدهٔ قبلی نداشته باشد (مثلاً اولین قیمت یک روز جدید)، آن قیمت به‌تنهایی
  باعث اجرای هشدار نمی‌شود و هشدار تا رخداد بعدی فعال می‌ماند. قفل‌ها درون‌فرآیندی هستند (یک نمونه
  اجرا می‌شود) و ماندگاری روی یک فایل JSON اتمیک انجام می‌شود؛ اجرای چند نمونه هم‌زمان پشتیبانی
  نمی‌شود (مثل فاز ۱ و ۲). نوتیفیکیشن به آخرین چتی ارسال می‌شود که کاربر از آن با ربات تعامل کرده
  است و اگر آن چت در دسترس نباشد، به شناسه پلتفرمی کاربر برمی‌گردد. ویرایش هشدار فقط «مقدار هدف» را
  تغییر می‌دهد؛ تغییر نماد یا نوع هشدار به معنی ساخت یک هشدار تازه است.

## 4.4 هوش بازار (Phase 4)

مسیر کاربر: `📊 بازار` → 📊 گزارش امروز | 📈 حرکت بازار | 🕐 آخرین بروزرسانی → (در گزارش امروز)
📋 گزارش کامل. همه صفحه‌ها فقط از «وضعیت بازار تأییدشده» فاز ۱ ساخته می‌شوند.

* **گزارش روزانه:** برای هر نماد رجیستری که قیمت معتبر دارد، «شروع روز» (اولین قیمت معتبر همان روز
  به وقت تهران)، «اکنون» (آخرین قیمت معتبر)، «بیشترین» و «کمترین» روز و «تغییر روزانه» نمایش داده
  می‌شود. تغییر روزانه = `اکنون − شروع روز` و درصد آن `(تغییر ÷ شروع روز) × ۱۰۰` است؛ اگر شروع روز
  صفر یا نامعتبر باشد، هم مبلغ و هم درصد به‌صورت `—` نشان داده می‌شوند (بدون تقسیم بر صفر و بدون
  عدد ساختگی). اولین قیمت معتبر روز، شروع/سقف/کف/اکنون را برابر می‌کند (تغییر صفر).
* **حرکت بازار (Movement) ≠ تغییر روزانه:** حرکت = `اکنون − آخرین قیمت معتبر قبلی` (مبنای مقایسه،
  آخرین قیمت *تأییدشده* قبلی است، نه شروع روز) و هم مقدار مطلق و هم درصد آن نمایش داده می‌شود، با جهت
  `UP`/`DOWN`/`UNCHANGED`/`UNKNOWN`.
  این دو عدد هیچ‌وقت با هم اشتباه گرفته نمی‌شوند: صفحه گزارش روزانه تغییر روزانه را نشان می‌دهد و صفحه
  حرکت بازار تغییر نسبت به آخرین بروزرسانی را. اگر قیمت معتبر قبلی وجود نداشته باشد، به‌جای عدد
  «— قیمت معتبر قبلی در دسترس نیست.» نمایش داده می‌شود.
* **آخرین بروزرسانی و کهنگی:** برای هر نماد، زمان واقعی دریافت آخرین قیمت معتبر (به وقت تهران،
  `Asia/Tehran`) به‌همراه برچسب `✅ تازه` یا `⚠️ کهنه` و در صفحه‌های گزارش در صورت وجود داده کهنه،
  هشدار «آخرین قیمت معتبر …» نمایش داده می‌شود. هر snapshot یک وضعیت تازگی تجمیعی هم دارد:
  `FRESH` (همه نمادها تازه)، `STALE` (داده هست ولی هیچ‌کدام تازه نیست)، `PARTIAL` (هم داده تازه هست و
  هم نماد کهنه/بدون داده) و `UNAVAILABLE` (هیچ داده معتبری نیست). آستانه کهنگی همان `PRICE_STALE_AFTER_MINUTES` فاز ۱
  است؛ فاز ۴ آستانه دومی معرفی نمی‌کند. آستانه کهنگی هرگز باعث حذف قیمت نمی‌شود: قیمت کهنه به‌عنوان
  «آخرین قیمت معتبر» و با برچسب صریح نشان داده می‌شود.
* **داده ناقص = نمایش صریح، نه جعل:** نمادهای ثبت‌شده که فاز ۱ برای آن‌ها قیمت معتبری ندارد، با پیام
  «⚠️ فعلاً اطلاعات معتبری در دسترس نیست.» فهرست می‌شوند؛ اگر هیچ نمادی داده معتبر نداشته باشد، صفحه
  پیام دوستانه «⚠️ در حال حاضر اطلاعات معتبر بازار در دسترس نیست.» را نشان می‌دهد. داده‌های رد‌شده یا
  ناهنجار (که هرگز وارد وضعیت بازار نمی‌شوند) در گزارش‌ها ظاهر نمی‌شوند.
* **خروجی خلاصه (فقط شمارش):** یک خط خلاصه توصیفی شامل تعداد نمادهای افزایشی/کاهشی/بدون تغییر/نامشخص
  بر مبنای *حرکت*؛ «نامشخص» هرگز با «بدون تغییر» جمع نمی‌شود. هیچ تحلیل، پیش‌بینی، سیگنال یا توصیه‌ای
  تولید نمی‌شود.
* **ترتیب و واحد:** ترتیب نمادها دقیقاً ترتیب رجیستری فاز ۱ است (طلا → سکه → ارز) و نماد از رجیستری
  اعتبارسنجی می‌شود؛ واحد داخلی همان واحد فاز ۱ (ریال/دلار) است و تبدیل واحد (ریال/تومان) فقط در زمان
  نمایش انجام می‌شود. هیچ رُندکردنی پیش از نمایش رخ نمی‌دهد. درصدهای این بخش با نشان فارسی `٪` و
  قیمت‌ها با ارقام فارسی نمایش داده می‌شوند (نشان `%` در صفحه‌های فاز ۱–۳ بدون تغییر مانده است).
* **بروزرسانی صفحه = فقط بازخوانی:** دکمه «↻ بروزرسانی» همین صفحه را از وضعیت معتبر موجود دوباره
  می‌سازد: نه فراخوانی API بیرونی، نه تغییر قیمت/آمار روزانه، نه جعل زمان، نه اجرای هشدار و نه تغییر
  علاقه‌مندی‌ها. هر رندر دقیقاً یک‌بار برای هر نماد از وضعیت بازار می‌خواند (بدون فراخوانی شبکه‌ای یا
  دیتابیسی به‌ازای هر نماد، بدون حلقه پس‌زمینه، بدون زیرساخت تازه، بدون cache دوم).
* **هم‌راستایی با هشدارها:** فاز ۴ هیچ رویدادی برای هشدارها تولید نمی‌کند و ارزیابی هشدار دو بار انجام
  نمی‌شود؛ مسیر هشدار همان مسیر چرخه بازار فاز ۱ → موتور فاز ۳ است.
* **خطای خواندن وضعیت:** اگر خواندن وضعیت یک نماد ناموفق باشد، همان نماد «بدون اطلاعات معتبر» گزارش
  می‌شود، دلیل فنی فقط در لاگ سرور ثبت می‌شود و بقیه گزارش سالم می‌ماند؛ خطای غیرمنتظره صفحه با پیام
  دوستانه «⚠️ دریافت اطلاعات بازار با مشکل مواجه شد.» پاسخ می‌گیرد (بدون افشای جزئیات فنی).

## 4.5 موتور کانال (Phase 5)

موتور کانال، لایهٔ انتشار محتوا است: هر پیامی که به کانال می‌رود از یک «آیتم محتوا» با نوع مشخص
ساخته می‌شود، با هویت منطقی یکتا ثبت می‌شود، و وضعیت ارسال آن برای **هر مقصد به‌صورت مستقل** پیگیری
می‌شود. این لایه هیچ داده‌ای نمی‌سازد: قیمت‌ها فقط از وضعیت تأییدشدهٔ فاز ۱ و آمار/تحلیل‌ها فقط از
لایهٔ توصیفی فاز ۴ می‌آیند.

### انواع پیام (دقیقاً ۷ نوع، بدون نوع دیگر)

| نوع | منبع داده | مسیر انتشار |
| --- | --- | --- |
| `PRICE_UPDATE` | وضعیت تأییدشدهٔ فاز ۱ | خودکار (زمان‌بندی همان چرخهٔ قیمت) |
| `MARKET_MOVEMENT` | حرکت تأییدشدهٔ فاز ۱ | خودکار، فقط با عبور از آستانه + cooldown |
| `DAILY_RANGE` | کمینه/بیشینهٔ واقعی روز (فاز ۱) | زمان‌بندی‌شده (پیش‌فرض خاموش) یا رویداد سقف/کف جدید |
| `DAILY_REPORT` | آمار روزانهٔ فاز ۴ | زمان‌بندی‌شده (پیش‌فرض خاموش) |
| `EDUCATIONAL` («گنجینه طلایی اتابک») | محتوای دستیِ ادمین | دستی: پیش‌نویس → تأیید → (زمان‌بندی) → انتشار |
| `BRANDED` | محتوای دستیِ ادمین | همان چرخهٔ ویرایشی |
| `NIGHTLY_ANALYSIS` («نگاه طلای اتابک») | محتوای دستی + بلوک داده‌ای فاز ۴ (اختیاری) | همان چرخهٔ ویرایشی، فقط در روز تهرانِ خودش |

هر نوع دیگر یا ناشناخته، در زمان ثبت رد می‌شود (`INVALID_MESSAGE_TYPE`)؛ رجیستری، تنها منبع مجاز
دامنهٔ «نوع پیام» است.

### چرخهٔ عمر محتوا (محرمانه، فقط ادمین)

`DRAFT → APPROVED → SCHEDULED → PUBLISHING → PUBLISHED | FAILED | CANCELLED`

* پیش‌نویس هرگز منتشر نمی‌شود؛ تأیید در **زمان اجرا دوباره بررسی می‌شود** (نه فقط در زمان زمان‌بندی).
* ویرایش محتوایی (عنوان/متن/رسانه/نوع) ⇒ `revision + 1` و بازگشت به `DRAFT` با پاک‌شدن
  `approvedAt/approvedBy/scheduledAt`؛ یعنی تغییر پس از تأیید، تأیید را باطل می‌کند.
* لغو (`CANCELLED`) یک کار زمان‌بندی‌شده را متوقف می‌کند و بازکردن دوباره (`reopen`) نسخهٔ جدید
  می‌سازد که تأیید تازه لازم دارد.
* تاریخچه هرگز بازنویسی یا پاک نمی‌شود؛ هر رکورد، دلیل شکست/رد خود را نگه می‌دارد.
* سطح ادمین فقط از راه `CHANNEL_ADMIN_USER_IDS` باز می‌شود و **هیچ API عمومی/بدون احراز هویت** برای
  مدیریت محتوا وجود ندارد؛ اگر این فهرست خالی باشد، سطح ادمین کامل غیرفعال است و برای کاربر عادی
  بی‌صدا (بدون افشای وجودش) رفتار می‌کند.
* دستورها در چت ادمین: `/content` (فهرست)، `/content show|new|media|market|approve|schedule|publish|cancel|reopen|help <id>`؛
  زمان‌بندی به وقت دیوار ساعت تهران (`YYYY-MM-DD HH:MM`) گرفته و به لحظهٔ مطلق UTC تبدیل می‌شود.

### جلوگیری از انتشار تکراری (Idempotency)

هر انتشار یک «هویت منطقی» دارد و همان هویت، کلید یکتای کار منتشرشده است:

* `PRICE_UPDATE` → `variant` + روز تهران + `HH:MM` + نمادها + مقصدها
* `MARKET_MOVEMENT` / `DAILY_RANGE` → نماد + روز + مقصد (رویدادها هویت قطعی دارند)
* `DAILY_REPORT` → روز تهران + مقصد
* محتوای ویرایشی → `contentId` + شمارهٔ نسخه + مقصد

قبل از هر ارسال، هویت بررسی می‌شود؛ اگر همان هویت قبلاً **موفق** شده باشد، ارسال تکرار نمی‌شود.
retry همان هویت اصلی را دوباره استفاده می‌کند و کارهای `SKIPPED` (مثلاً به‌خاطر نرسیدن داده) با همان
هویت قابل اجرای مجدد هستند — بدون تولید پیام تکراری.

### پیگیری ارسال به‌ازای هر مقصد

* یک کار می‌تواند هر دو مقصد (بله و تلگرام) را هدف بگیرد؛ برای هر مقصد یک `PublicationDelivery`
  با وضعیت `PENDING → SENDING → SENT | FAILED | UNKNOWN` ثبت می‌شود.
* موفقیت بله، شکست تلگرام را پنهان نمی‌کند و شکست یک مقصد، مقصد دیگر را متوقف نمی‌کند.
* دسته‌بندی خطا: `HTTP 5xx/429` = قابل retry، سایر `4xx` و `ok:false` = دائمی، **بدون پاسخ
  (timeout/قطع اتصال) = مبهم** — نتیجهٔ مبهم هرگز «موفق» ثبت نمی‌شود و به‌صورت خودکار هم retry نمی‌شود
  (`DELIVERY_OUTCOME_UNKNOWN`) تا پیام تکراری ساخته نشود.
* retry کران‌دار با backoff نمایی (`CHANNEL_PUBLICATION_MAX_ATTEMPTS`،
  `CHANNEL_PUBLICATION_RETRY_DELAY_MS`) و شمارندهٔ تلاش به‌صورت ماندگار؛ پس از موفقیت قطعی، retry انجام نمی‌شود.
* رسانه: اگر متن در محدودهٔ کپشن باشد، عکس با کپشن ارسال می‌شود؛ متن بلندتر اول به‌صورت پیام مستقل و
  سپس عکس می‌رود. شکست رسانه نتیجهٔ متنی را از بین نمی‌برد و جداگانه ثبت می‌شود
  (`mediaStatus`/`mediaError`).
* هیچ توکنی لاگ نمی‌شود (پاک‌سازی/redaction مشترک با فازهای قبل) و هیچ خطایی بی‌صدا بلعیده نمی‌شود.

### زمان‌بندی، تهران و رفتار کارهای از‌دست‌رفته

* همهٔ زمان‌ها صریحاً با `Asia/Tehran` و مستقل از TZ سرور محاسبه می‌شوند (توزیع دیوار ساعت تهران = UTC+3:30).
* یک tick دقیقه‌ای (`channel-engine-tick`) کارهای سررسیده را اجرا می‌کند؛ زمان‌های انتشار از پیکربندی
  خوانده می‌شوند (نه از cron جداگانه) و «یک‌بار در روز» با کلید ماندگار تضمین می‌شود؛ هم‌زمانی و
  ثبت cron تکراری ممکن نیست.
* کار از‌دست‌رفته (سرویس خاموش بوده) بر اساس مهلت `CHANNEL_MISSED_JOB_GRACE_MINUTES` تعیین تکلیف می‌شود:
  به‌روزرسانی بازارِ کهنه دور ریخته نمی‌شود ولی منتشر هم نمی‌شود (`SKIPPED` + دلیل ثبت‌شده)، محتوای
  ویرایشی در پنجرهٔ خودش منتشر می‌شود و «نگاه طلای اتابک» در روز تهرانِ نادرست هرگز منتشر نمی‌شود
  (`MISSED_WINDOW`). هیچ چیزی بی‌صدا حذف نمی‌شود.
* بازیابی پس از ری‌استارت: کارهای در جریان بررسی می‌شوند؛ اگر مقصدی `SENT` باشد کار `PUBLISHED` می‌شود و
  **هیچ‌چیز دوباره فرستاده نمی‌شود**، نتیجهٔ مبهم بدون retry به `FAILED` می‌رود، و کارهای منقضی
  `SKIPPED` می‌شوند. پیش از انتشار تأخیریِ پیام‌های بازار، صلاحیت داده‌ها **دوباره** ارزیابی می‌شود
  (تازگی، نماد، آمار روزانه) و لغو/تأیید نیز دوباره کنترل می‌شود.

### قواعد داده (بدون جعل) و دلایل رد

* فقط وضعیت تأییدشدهٔ فاز ۱ و خروجی توصیفی فاز ۴؛ فرمترها هیچ‌وقت قیمت نمی‌گیرند، آمار روزانه را
  تغییر نمی‌دهند، هشدار اجرا نمی‌کنند و اعتبارسنجی را دور نمی‌زنند.
* مقدار ناموجود هرگز صفر نمی‌شود و «بدون timestamp» هرگز «الان» نمی‌شود؛ دادهٔ کهنه صریح برچسب می‌خورد.
* دلیل‌های رد به‌صورت تایپ‌دار: `INVALID_MARKET_SNAPSHOT`، `STALE_MARKET_DATA`،
  `MISSING_REQUIRED_SYMBOL`، `INVALID_DAILY_STATISTICS`، `CONTENT_NOT_APPROVED`، `PUBLICATION_CANCELLED`،
  `DUPLICATE_PUBLICATION`، `DESTINATION_UNAVAILABLE`، `MOVEMENT_BELOW_THRESHOLD`،
  `RANGE_EVENT_SUPPRESSED`، `TYPE_DISABLED`، `MISSED_WINDOW`، `CONTENT_NOT_PUBLISHABLE`.
* آستانهٔ حرکت هر نماد قابل تنظیم است (سراسری + بازنویسی اختصاصی)؛ **نبود آستانه به معنای انتشار
  بی‌قید نیست**: پیش‌فرض امن و مستند اعمال می‌شود و مقدار `0` فقط به‌صورت آگاهانه همان نماد را خاموش می‌کند.
* هیچ تحلیل، پیش‌بینی، سیگنال یا توصیه‌ای تولید نمی‌شود؛ پیام‌های ویرایشی هم فقط محتوای تأییدشدهٔ
  ادمین هستند.

### پیکربندی (۲۱ کلید `CHANNEL_*`)

`CHANNEL_DATA_FILE`، `CHANNEL_ADMIN_USER_IDS`، `CHANNEL_MAX_CONTENT_CHARS`،
`CHANNEL_MEDIA_CAPTION_LIMIT`، `CHANNEL_HISTORY_LIMIT`، `CHANNEL_PUBLICATION_MAX_ATTEMPTS`،
`CHANNEL_PUBLICATION_RETRY_DELAY_MS`، `CHANNEL_MISSED_JOB_GRACE_MINUTES`،
`CHANNEL_MOVEMENT_THRESHOLD_PERCENT`، `CHANNEL_MOVEMENT_THRESHOLD_OVERRIDES`،
`CHANNEL_MOVEMENT_COOLDOWN_MINUTES`، `CHANNEL_DAILY_RANGE_ENABLED`، `CHANNEL_DAILY_RANGE_TIME`،
`CHANNEL_DAILY_RANGE_EVENTS_ENABLED`، `CHANNEL_DAILY_RANGE_COOLDOWN_MINUTES`،
`CHANNEL_DAILY_REPORT_ENABLED`، `CHANNEL_DAILY_REPORT_TIME` (به‌همراه کلیدهای مشترک کانال که در ادامه
فهرست شده‌اند). فاز ۶ دو کلید دیگر به همین خانواده اضافه می‌کند: `CHANNEL_CTA_ENABLED` و
`CHANNEL_CTA_ROUTES` (به‌همراه `BALE_BOT_USERNAME`، `TELEGRAM_BOT_USERNAME`، `TELEGRAM_CHANNEL_URL`
و `BOT_CHANNEL_INVITE_ENABLED` که در بخش ۴.۶ توضیح داده شده‌اند). همه در `.env.example` و جدول بخش ۵ مستند شده‌اند؛ مقادیر در زمان startup اعتبارسنجی
می‌شوند. `CHANNEL_DAILY_RANGE_ENABLED` و `CHANNEL_DAILY_REPORT_ENABLED` عمداً پیش‌فرض `false` هستند،
چون روشن‌کردنشان ریتم انتشار کانال را تغییر می‌دهد و باید تصمیم آگاهانهٔ اپراتور باشد.

## 4.6 پیوند کانال و بات (Phase 6)

کانال و بات یک اکوسیستم واحد را می‌سازند: **کانال = سطح توزیع** و **بات = سطح تعامل**. هیچ‌کدام
جای دیگری را پیاده‌سازی نمی‌کند؛ قیمت‌ها همچنان فقط از فاز ۱، هشدارها از فاز ۳، تحلیل‌ها از فاز ۴ و
انتشار/تأیید/زمان‌بندی از فاز ۵ می‌آید.

### کانال ← بات (دکمه روی پیام‌های کانال)

* سیاست دکمه در `CtaPolicyService` تعیین می‌شود و **هیچ‌جا دادهٔ بازار نمی‌خواند و وضعیتی را تغییر
  نمی‌دهد**؛ فقط «آیا این پیام می‌تواند دکمه داشته باشد و به کجا برود؟» را پاسخ می‌دهد.
* ترتیب تصمیم: ۱) انتخاب صریح ادمین روی خود آیتم (`/content cta <id> <choice>`)، ۲) بازنویسی
  پیکربندی (`CHANNEL_CTA_ROUTES`)، ۳) پیش‌فرض رجیستری نوع پیام (با پالایش بر پایهٔ گروه نمادها).
* پیش‌فرض‌ها: `PRICE_UPDATE`/`MARKET_MOVEMENT`/`DAILY_RANGE` → بر پایهٔ نمادها `gold` یا `coin` و
  در حالت عمومی/ترکیبی `prices`؛ `DAILY_REPORT`/`NIGHTLY_ANALYSIS` → `prices`؛
  `EDUCATIONAL`/`BRANDED` → **بدون دکمه**. به‌این‌ترتیب «به‌روزرسانی معمول قیمت» هرگز دکمهٔ هشدار
  نمی‌گیرد و محتوای آموزشی بی‌ربط، دکمهٔ تبلیغاتی نمی‌گیرد.
* دکمهٔ هشدار (`alert`) فقط با انتخاب صریح ادمین روی یک آیتم ساخته می‌شود (فاز ۵ نوع «تبلیغ» ندارد و
  نوع هشتم ساخته نشد).
* لینک هر مقصد جداگانه ساخته می‌شود: `https://ble.ir/<BALE_BOT_USERNAME>?start=<route>` و
  `https://t.me/<TELEGRAM_BOT_USERNAME>?start=<route>`. اگر نام کاربری یا لینک یک پلتفرم تنظیم نشده
  باشد، پیام **بدون دکمه** منتشر می‌شود (هرگز لینک جعلی/ناقص ساخته نمی‌شود) و هیچ مقصدی به‌خاطر
  نبود دکمه از انتشار بازنمی‌ماند.
* رکورد هر ارسال (`PublicationDelivery.ctaRoute`) ثبت می‌کند که **واقعاً چه دکمه‌ای ارسال شد**
  (`null` = بدون دکمه). اگر ارسال با خطا مواجه شود، دکمه «ارسال‌شده» ثبت نمی‌شود.
* دکمه فقط روی **پیام اصلی** می‌نشیند: در حالت عکس با متن کوتاه روی کپشن، و در متن بلند روی پیام
  متنی (هرگز دو بار).

### بات ← کانال

* منوی اصلی دکمهٔ `📢 کانال طلای اتابک` را دارد: اگر لینک کانال پلتفرم تنظیم شده باشد دکمهٔ URL
  ساخته می‌شود، وگرنه متن توضیح امن نمایش داده می‌شود (بدون دکمهٔ بی‌مقصد).
* چهار صفحهٔ گزارش بازار (گزارش امروز، گزارش کامل، حرکت بازار، آخرین بروزرسانی) یک ردیف دعوت
  مشترک می‌گیرند: `📢 تحلیل کامل‌تر بازار در کانال طلای اتابک` + دکمهٔ `📢 دیدن تحلیل در کانال`.
  این خط **فقط** به این چهار پاسخ اضافه می‌شود (بدون فوتر سراسری)، هیچ آماری را تکرار یا بازنویسی
  نمی‌کند و هیچ زمان انتشار یا ادعای تکمیل‌بودن گزارش را مطرح نمی‌کند.

### لینک‌های عمیق (`/start <payload>`)

| payload | نتیجه |
| --- | --- |
| `alert` | ورود به **ویزارد موجود** فاز ۳ (هیچ هشداری خودکار ساخته نمی‌شود) |
| `prices` | همان صفحهٔ قیمت‌های فاز ۱ |
| `coin` | همان صفحهٔ سکه |
| `gold` | همان صفحهٔ طلا |
| `channel` | صفحهٔ کانال با لینک تنظیم‌شده یا پاسخ امن |
| سایر مقادیر | منوی اصلی + لاگ تشخیصی (هیچ قابلیتی فعال نمی‌شود، هیچ خطایی رخ نمی‌دهد) |
| بدون مقدار | همان `/start` پیش‌فرض (صفحهٔ خوش‌آمد) |

* پارس پیام از اجرا جدا است: `parseStartPayload` فقط توکن دوم را می‌خواند (`/start` بعد از
  نرمال‌سازی حروف کوچک)، طول بیشتر از ۳۲ کاراکتر یا نویسه‌های غیرمجاز را `unknown` می‌کند و توکن‌های
  اضافی را نادیده می‌گیرد (توکن دوم هرگز مسیر/نماد/دسترسی تازه نمی‌سازد).
* payload ورودی غیرقابل‌اعتماد است: فقط شناسه‌های تأییدشدهٔ پنج‌گانه پذیرفته می‌شوند، هیچ مقصد
  دلخواهی ساخته نمی‌شود، هیچ عملیات مدیریتی از راه لینک اجرا نمی‌شود، و هیچ مسیری اعتبارسنجی هشدار
  را دور نمی‌زند (`alert` فقط ویزارد موجود را باز می‌کند و ادامهٔ کار همان اعتبارسنجی/ذخیره‌سازی
  فاز ۳ است).
* سقف هشدارهای کاربر و قواعد فاز ۳ دست‌نخورده باقی مانده است.

## 10. Cron schedules (Timezone: `Asia/Tehran`)

| Job | زمان‌بندی | Cron expression | انتشار |
| --- | --- | --- | --- |
| به‌روزرسانی قیمت (نیم‌ساعتی) | ۰۸:۰۰ تا ۲۱:۳۰، هر ۳۰ دقیقه | `0 0,30 8-21 * * *` | پیام قیمت کانال |
| به‌روزرسانی پایانی روز | ۲۲:۰۰ | `0 0 22 * * *` | پیام قیمت کانال |
| گزارش پوستر | ۱۲:۱۵، ۱۶:۱۵، ۱۹:۱۵ | `15 12,16,19 * * *` | متن پوستر |
| tick موتور کانال | هر دقیقه (ثانیهٔ ۵) | `5 * * * * *` | کارهای سررسیدهٔ زمان‌بندی‌شده، انتشار محتوا، سقف/کف و گزارش روزانه (بر پایهٔ مقادیر پیکربندی) |

* همه زمان‌ها صریحاً با `timeZone: 'Asia/Tehran'` اجرا می‌شوند تا مستقل از TZ سرور باشند.
* ساعت گزارش پوستر از ۱۲:۰۰/۱۶:۰۰/۱۹:۰۰ به ۱۲:۱۵/۱۶:۱۵/۱۹:۱۵ منتقل شده است، چون در زمان قبلی دقیقاً
  هم‌زمان با به‌روزرسانی نیم‌ساعتی اجرا می‌شد و دو پیام را در یک دقیقه منتشر می‌کرد.
* علاوه بر این، یک «قفل انتشار» تضمین می‌کند تا وقتی یک انتشار در جریان است، اجرای هم‌زمان دیگری پیام
  تکراری نفرستد.
* موتور کانال (فاز ۵) به‌جای cron جداگانه برای هر ساعت پیکربندی‌شده، یک tick دقیقه‌ای دارد؛ ثبت
  هم‌زمان/تکراری cron رخ نمی‌دهد و «یک‌بار در روز» با کلید یکتای ماندگار تضمین می‌شود.

## 11. Failure behaviour

* خطای API قیمت: بدون انتشار هیچ پیامی، بدون قیمت جعلی؛ خطا با context در لاگ ثبت می‌شود.
  تنها خطاهای گذرا (شبکه، تایم‌اوت، HTTP 5xx، HTTP 429) با backoff نمایی دوباره تلاش می‌شوند.
* خطای ارسال: برای هر پلتفرم نتیجه جدا (`success: false` + متن خطای پاک‌سازی‌شده) برگردانده می‌شود؛
  لاگ هرگز موفقیت کاذب ثبت نمی‌کند و توکن‌ها در لاگ‌ها ماسک می‌شوند.
* روند قیمت: پایه مقایسه فقط با آخرین قیمتِ معتبر در همان روز تهران به‌روز می‌شود و در شروع روز جدید بازنشانی
  می‌گردد؛ بنابراین اولین پیام روز با قیمت دیروز مقایسه نمی‌شود.
* داده نامعتبر یا ناهنجار: قیمت رد می‌شود، دلیل آن (`OUT_OF_RANGE`, `EXCESSIVE_CHANGE`, ...) در لاگ و در
  هشدار ادمین ثبت می‌شود و وضعیت معتبر قبلی نماد در حافظه/فایل باقی می‌ماند؛ هیچ آمار روزانه‌ای آلوده نمی‌شود.
* قیمت کهنه (`STALE` بعد از `PRICE_STALE_AFTER_MINUTES`): به‌عنوان «تازه» منتشر نمی‌شود و نماد لنگر
  انتشار محسوب نمی‌شود؛ اما به‌عنوان «آخرین قیمت معتبر» در دسترس است.
* بازیابی: به‌محض رسیدن یک قیمت سالم بعد از یک ناهنجاری، همان چرخه مجدداً قابل انتشار می‌شود (بدون
  retry بی‌پایان و بدون شمارنده‌ی فرسایشی).
* خطای انتشار در موتور کانال (فاز ۵): شکست یک مقصد، مقصد دیگر را متوقف نمی‌کند؛ خطای گذرا با
  backoff کران‌دار دوباره تلاش می‌شود، خطای دائمی به‌صورت قابل‌مشاهده (`FAILED` + `lastError`) ثبت
  می‌شود و نتیجهٔ مبهم (`UNKNOWN`) هرگز موفق یا به‌صورت خودکار retry نمی‌شود. هر کار فقط در صورت
  موفقیت همهٔ مقصدها `PUBLISHED` می‌شود و دلیل هر رد/شکست در تاریخچه باقی می‌ماند.

## 12. Deployment notes

* حداقل متغیرهای لازم برای استقرار: `PRICE_API_URL`، `BALE_BOT_TOKEN`، `BALE_CHANNEL_ID`
  (برای آینه‌کردن به تلگرام: `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHANNEL_ID`).
* کانتینر روی پورت `3000` گوش می‌دهد و به `0.0.0.0` بایند می‌شود؛ برای پلتفرم‌های PaaS کافی است `PORT` را ست کنند.
* `/health` را به health check پلتفرم وصل کنید (پاسخ ۲۰۰ = سالم).
* اسرار را فقط از راه متغیرهای محیطی/secret manager تزریق کنید؛ هرگز در ایمیج یا ریپو قرار ندهید.
* وضعیت بازار در `MARKET_STATE_FILE` (پیش‌فرض `./data/market-state.json`) و داده کاربران/علاقه‌مندی‌ها
  در `USER_DATA_FILE` (پیش‌فرض `./data/users.json`) ذخیره می‌شود. برای حفظ آن بین
  ری‌استارت‌ها یک volume به مسیر داده وصل کنید:
  `docker run -v atabak-data:/app/data ...` یا در compose: `volumes: ["atabak-data:/app/data"]`.
  اگر فایل خالی/خراب باشد برنامه بالا می‌آید و وضعیت را از صفر می‌سازد (بدون داده جعلی).
* اگر `ANOMALY_ALERT_CHAT_ID` خالی باشد، هشدارهای ناهنجاری فقط در لاگ ثبت می‌شوند و هیچ پیامی به کانال
  کاربران نمی‌رود.
* فایل ماندگاری هشدارها و رکوردهای ارسال در `ALERTS_DATA_FILE` (پیش‌فرض `./data/alerts.json`) است؛
  همان مسیر داده را (مثل بالا) روی یک volume نگه دارید تا هشدارها و وضعیت اجرای آن‌ها بین
  ری‌استارت‌ها حفظ شود.
* فایل `CHANNEL_DATA_FILE` (پیش‌فرض `./data/channel.json`) محتوای ویرایشی، کارهای انتشار، وضعیت ارسال
  هر مقصد و رویدادهای حرکت/سقف‌کف را نگه می‌دارد. بدون volume، پس از ری‌استارت تاریخچه و کلیدهای
  جلوگیری از تکرار از دست می‌رود (برنامه بالا می‌آید و وضعیت را از صفر می‌سازد، بدون داده جعلی).
  برای فعال‌کردن سطح مدیریت محتوا باید `CHANNEL_ADMIN_USER_IDS` ست شود؛ در غیر این صورت این سطح
  کاملاً خاموش است.
